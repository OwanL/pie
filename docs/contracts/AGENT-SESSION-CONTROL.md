# Agent session control

Pie registers a worker-local `session_control` tool for primary agent turns and their initial-context inventory. The shared [`harness/agent-processes/coordinator/backend-tools.ts`](../../harness/agent-processes/coordinator/backend-tools.ts) factory supplies it; only the primary runtime gets the worker transport. The tool is a typed worker-to-coordinator bridge, not a general worker RPC tunnel. Its definition is in [`harness/tools/session-control/index.ts`](../../harness/tools/session-control/index.ts); the coordinator owns resolution and operation composition in [`harness/agent-processes/coordinator/server.ts`](../../harness/agent-processes/coordinator/server.ts). In-memory subagents cannot use it. The scope is the current extension host; there is no cross-window federation.

## Actions and targets

The tool accepts `list`, `create`, `read`, `message`, `settings.get`, `settings.set`, and `close`. Paths are not tool arguments.

| Action | Inputs and behavior |
| --- | --- |
| `list` | No target. Returns a bounded `scope: "current-extension-host"` view of live membership, assigned titles and provisional labels, `activity` (`idle`, `running`, or `waiting-user-input`), coordinator `busy` and runtime state, running-tool/subagent counts, current-request start time and elapsed milliseconds, and available cumulative working-time/cost evidence. `membershipHydrated` and `titleNamespaceReady` are separate; `totalCount`, `sessionsTruncated`, and `truncated` report limits. A `closing` collection may identify closing reservations. Closed history is not listed. This is not an archive browser or monitoring API. |
| `create` | Requires `title` (a non-empty single line of 1–25 characters after trimming); optional `cwd`, `prompt`, and `settings`. It creates a cold session, durably marks agent-created provenance, assigns and persists its unique title before publication, captures the creator's saved model, reasoning, system-prompt toggles, and execution settings once, and applies supplied overrides. Omitted `cwd` uses the creator session's durable working directory; explicit `cwd` wins. Publication adds an ordinary background tab without changing selection and gives it the `Agent-created session` tooltip. Only after successful configuration does optional `prompt` use ordinary `message.send`; without a prompt the session remains cold and idle. |
| `read` | Requires `title` or `self: true`. `direction` is `latest` by default; `limit` is 1–64 (default 32). The first page is `latest`; later `older`/`newer` pages require the returned `{start,end}` cursor. Reads are bounded transcript pages for a live session. |
| `message` | Requires non-empty `prompt` and exactly one of `title`, `self: true`, or `replyTo`. `replyTo` is accepted only here and cannot be combined with `title` or `self`. Optional `settings` is a persistent target-session patch applied before sending. Idle targets start a turn; busy targets use ordinary queued-send behavior. |
| `settings.get` | Requires `title` or `self: true`. Returns `{sessionPath, settings}` where settings contains `model: {provider,id}`, `reasoning`, `autonomousMode`, `subagentProviderChoices`, and `disabledSystemPromptEntries`. |
| `settings.set` | Requires `title` or `self: true` and a non-empty `settings` patch. Returns `{sessionPath, configuration}`; `configuration.status` is `succeeded`, `failed`, or `unknown`, with applied fields and, on failure, the failing setting and error. A persisted host-preference update may report `hostApplicationPending` while runtime application catches up. |
| `close` | Requires `title` or `self: true`; optional `delete: true` selects the existing privacy/deletion lifecycle. Close stops active and queued work, removes the tab, and uses host-owned cleanup. |

Fields that do not apply to the selected action are rejected rather than silently discarded. For every existing-session action, omitted or conflicting target selectors are errors; there is no implicit caller default. `self: true` works for an unnamed caller. `title` resolves only an assigned live title, exactly after trimming outer whitespace; provisional display labels do not resolve. Startup title reconciliation must finish before title lookup/allocation is available. Titles are unique among live sessions, persisted before publication, and newly assigned base titles use a 25-character limit; automatic collision suffixes are additional. A title identifies its current live owner, not a permanent identity across close and title reuse; this does not require an additional identity selector. See [session titles](SESSION-TITLES.md).

The settings patch accepts these optional fields: `model: {provider,id}`, `reasoning`, `autonomousMode`, `subagentProviderChoices: Record<string,boolean>`, and `disabledSystemPromptEntries: string[]`. Updates use the existing model, prompt-toggle, and host preference owners, including their validation and busy-session rules; they do not edit shared application defaults. Internal cold model-settings metadata reads skip context inventory discovery; public cold opens and cold prompt-toggle publications still discover fresh inventories. MCP inheritance, inspection, and update are deferred; new sessions use normal MCP discovery for their own directory.

## Outcomes, provenance, and lifecycle

Create reports separate `creation`, `configuration`, and `message` outcomes. If saved-setting inheritance fails before durable creation is admitted, `creation.status` is `not_created`, configuration is `not_started`, and the optional prompt is `not_sent`; no new session or tab exists. A failure after creation is admitted may instead be `unknown`, which never authorizes automatic recreation. Settings writes report `configuration` status and applied fields; message acceptance reports `accepted` (and `queued` when applicable), `rejected`, `unknown`, or `not_sent`. A configuration failure—including a busy-setting rejection—prevents that call's prompt from being sent, but does not roll back settings already applied or remove the created session. A send failure leaves the configured session. Agent-send admission is rechecked against authoritative live membership after configuration and again after asynchronous runtime promotion; a completed close rejects later delivery without rolling back durable creation or configuration. Missing acknowledgements remain unknown unless existing operation evidence resolves them. Worker acknowledgement deadlines and unconfirmed durable sender attribution report message `unknown`, not a definitive rejection, even if the recipient is already running. Model/reasoning and prompt-toggle worker acknowledgement deadlines likewise report configuration `unknown`, and the optional prompt is `not_sent`. Combined create/configure/send is not atomic, has no compound recovery/status API, and is never automatically replayed; a fresh create request is a new create. Cancellation rejects the worker request but does not roll back an already-admitted coordinator operation; late results are dropped by request identity. A thrown transport/cancellation error for create, message, settings update, or close reports tool-level `outcome: unknown` and warns that the operation may continue: do not automatically repeat the mutation. Local validation and acknowledged rejections retain their known-failure behavior.

For every cross-session message, including `create.prompt`, the coordinator derives sender identity from the calling worker, adds the sender identity/title (when assigned) and identity-bound `replyReference` to the recipient's model input, and publishes an Agent-attributed user-role transcript row with an Agent/bot cue. A send rejected before acceptance removes its optimistic row. The owning worker attaches authenticated sender provenance to the SDK user message at its durable append boundary; reload reads that embedded metadata (legacy `pie.agent-message-provenance` sidecars remain readable). Transcript display removes exactly one canonical sender envelope only when it matches validated persisted sender metadata, retaining attribution separately; durable model input is unchanged. This keeps the SDK echo comparable to its optimistic Agent row without showing the model-only envelope as message text. Unprovenanced or mismatched lookalikes remain user content. An idle send does not report accepted until its user entry has been persisted. The initial SDK user `message_start` preserves the direct request's attribution, including when a follow-up is already queued; only a later queued delivery consumes that queue's identity. On a fresh session the worker explicitly writes the buffered SDK entries at the user append boundary rather than waiting for the first assistant response; this is message acceptance, not answer completion. Queued acceptance acknowledges only enqueueing, not durable delivery; attribution travels with the user entry and is checked at delivery. If provenance cannot be confirmed after admission, the operation is partial/unknown and emits an ambiguous operational error rather than claiming durable success. `replyTo` resolves that stable sender identity only while its original session is live; it is not a title alias, operation token, or cross-host address. Title reuse never redirects it. Attribution does not create an automatic reply obligation.

There is no agent-facing `stop` action. `close` is the stop-and-close action. It admits any explicitly targeted live session, not just sessions created by the caller. New execution is fenced once closing starts. Pending agent prompts retain their pre-configuration cancellation generation through runtime promotion; closing invalidates it even if the same durable session is later reopened. A fresh request after reopening is admitted normally, and unrelated session changes do not invalidate that generation. Closing another session waits for confirmed host stop/cleanup or reports failure/unknown. Self-close returns `closeRequested` only after the host accepts responsibility; host cleanup is handed off after the response so the caller can stop without claiming close completion. Repeated closes join the owning operation. A hidden running target still uses stop/cleanup. When no tab or hidden running target exists, retained history alone cannot prove completion: the host requires a matching successful prior close barrier and no newer live/pending state, otherwise it reports unknown. A close of a pending create cancels queued sends; a late durable create is cleaned up, not reopened. A non-private close retains on-disk history but removes live addressability; delete uses the existing irreversible deletion path.

Tool inputs/results and transcript projections are bounded before worker IPC. Agent transcript reads retain conversation content, IDs, status, and sender attribution, but omit renderer/accounting/debug metadata and duplicated content mirrors. Tool inputs/results use bounded previews with explicit truncation/omission indicators; SDK result `details` and image base64 bodies are not returned. Image metadata remains with `omitted: true`. This projection is applied before the page byte budget, so bulky renderer diagnostics do not make otherwise readable conversation rows unavailable. Queued steering/follow-up delivery keeps the active tool/skill selection without another skill-pruning prepass, regardless of whether the message came from a user or an agent. An idle-session request, including `create.prompt`, uses normal pruning. There is no agent-origin bypass. See [tool and skill selection](../../harness/tool-and-skill-selection/README.md#integration).
