# Agent session control

Pie registers a worker-local `session_control` tool for primary agent turns and their initial-context inventory. The shared [`harness/agent-processes/coordinator/backend-tools.ts`](../../harness/agent-processes/coordinator/backend-tools.ts) factory supplies it; primary runtimes get the full worker transport, while in-memory subagents get a read-only bridge for discovery and transcript reads. The tool is a typed worker-to-coordinator bridge, not a general worker RPC tunnel. Its definition is in [`harness/tools/session-control/index.ts`](../../harness/tools/session-control/index.ts); the coordinator owns resolution and operation composition in [`harness/agent-processes/coordinator/server.ts`](../../harness/agent-processes/coordinator/server.ts). Subagents cannot create, message, configure, close, clean up, or inspect mutation operations. The scope is the current extension host; there is no cross-window federation.

## Actions and targets

The tool accepts `list`, `create`, `read`, `message`, `settings.get`, `settings.set`, `close`, `cleanup`, and `operation.status`. Paths are not tool arguments.

| Action | Inputs and behavior |
| --- | --- |
| `list` | No target. Returns a bounded `scope: "current-extension-host"` view of live membership, assigned titles and provisional labels, caller-specific `ownedByCaller` and durable creator identity when known, `activity` (`idle`, `running`, or `waiting-user-input`), coordinator `busy` and runtime state, running-tool/subagent counts, current-request start time and elapsed milliseconds, and available cumulative working-time/cost evidence. `membershipHydrated` and `titleNamespaceReady` are separate; `totalCount`, `sessionsTruncated`, and `truncated` report limits. A `closing` collection may identify closing reservations. Closed history and snoozed sessions are not listed. Snoozed sessions are not addressable until restored; see [session snooze](STATE_CONTRACT.md#session-snooze). This is not an archive browser or monitoring API. |
| `create` | Requires `title` (a non-empty single line of 1–25 characters after trimming) and `bucket` (`small`, `medium`, or `frontier`); optional `cwd`, `prompt`, and `settings`. `settings.model` is rejected. It creates a cold session, durably marks agent-created provenance and creator identity, assigns and persists its unique title before publication, selects a model and reasoning by bucket, captures the creator's saved system-prompt toggles and execution settings once, and applies supplied overrides. Omitted `cwd` uses the creator session's durable working directory; explicit `cwd` wins. Publication adds an ordinary background tab without changing selection and gives it the `Agent-created session` tooltip. Only after successful configuration does optional `prompt` use ordinary `message.send`; without a prompt the session remains cold and idle. |
| `read` | Requires `title` or `self: true`. Returns completed conversation content, including incoming messages, plus a compact live activity header. `maxCharacters` defaults to 4,000; callers can increase it up to 262,144. Reasoning and tool inputs/results are excluded unless `includeReasoning` or `includeToolCalls` is true. `direction` defaults to `latest`; `older`/`newer` use the returned cursor to retrieve unseen content. |
| `message` | Requires non-empty `prompt` and exactly one of `title`, `self: true`, or `replyTo`. `replyTo` is accepted only here and cannot be combined with `title` or `self`. Optional `settings` is a persistent target-session patch applied before sending. Idle targets start a turn; busy targets use ordinary queued-send behavior. |
| `settings.get` | Requires `title` or `self: true`. Returns `{sessionPath, settings}` where settings contains `model: {provider,id}`, `reasoning`, `autonomousMode`, `subagentProviderChoices`, and `disabledSystemPromptEntries`. |
| `settings.set` | Requires `title` or `self: true` and a non-empty `settings` patch. Returns `{sessionPath, configuration}`; `configuration.status` is `succeeded`, `failed`, or `unknown`, with applied fields and, on failure, the failing setting and error. A persisted host-preference update may report `hostApplicationPending` while runtime application catches up. |
| `close` | Requires `title` or `self: true`; optional `delete: true` selects the existing privacy/deletion lifecycle. Close stops active and queued work, removes the tab, and uses host-owned cleanup. |
| `cleanup` | Closes live sessions created by the caller through ordinary close, retaining normal history and honoring private-session deletion. `dontCloseRunning` defaults to true; false includes running sessions. Reports per-session outcomes and skips. Human steering does not change creator ownership. |
| `operation.status` | Inspects a caller-owned mutation receipt without replaying the action. Unknown or unavailable evidence is not proof that the action did not happen. |

Fields that do not apply to the selected action are rejected rather than silently discarded. For every existing-session action, omitted or conflicting target selectors are errors; there is no implicit caller default. `self: true` works for an unnamed caller. `title` resolves only an assigned live title, exactly after trimming outer whitespace; provisional display labels do not resolve. Startup title reconciliation must finish before title lookup/allocation is available. Titles are unique among live sessions, persisted before publication, and newly assigned base titles use a 25-character limit; automatic collision suffixes are additional. A title identifies its current live owner, not a permanent identity across close and title reuse; this does not require an additional identity selector. See [session titles](SESSION-TITLES.md).

For create, choose `small` for simple tasks, `medium` for well-defined substantial tasks, and `frontier` for hard reasoning. Model candidates are filtered by the caller's provider policy and enabled/eligible availability. Selection falls back in descending bucket order (`frontier` → `medium` → `small`, starting at the requested bucket); after exhaustion, the caller's model is a fallback only if eligible and enabled. The selected assignment supplies reasoning unless `settings.reasoning` overrides it; caller-model fallback inherits the caller's saved reasoning. Selection uses the caller's saved subagent provider choices, not any provider-choice override intended for the new session. The selected model and effective reasoning must also be available and eligible in the creation-time provider runtime before durable creation is admitted. These are independent primary sessions, not nested subagents: subagent nesting rules and always-parent model semantics do not apply.

The settings patch accepts these optional fields (except `model` on create): `model: {provider,id}`, `reasoning`, `autonomousMode`, `subagentProviderChoices: Record<string,boolean>`, and `disabledSystemPromptEntries: string[]`. Updates use the existing model, prompt-toggle, and host preference owners, including their validation and busy-session rules; they do not edit shared application defaults. Internal cold model-settings metadata reads skip context inventory discovery; public cold opens and cold prompt-toggle publications still discover fresh inventories. MCP inheritance, inspection, and update are deferred; new sessions use normal MCP discovery for their own directory.

## Outcomes, provenance, and lifecycle

Create reports separate `creation`, `configuration`, and `message` outcomes. After configuration is attempted, `modelSelection` identifies the selected provider/model, assignment reasoning, requested/effective bucket, eligible pool, and caller-model fallback; `configuration.reasoning` reports the effective reasoning after any override. If saved-setting capture or model-selection preflight fails before durable creation is admitted, `creation.status` is `not_created`, configuration is `not_started`, and the optional prompt is `not_sent`; no new session or tab exists. A failure after creation is admitted may instead be `unknown`, which never authorizes automatic recreation. Settings writes report `configuration` status and applied fields; message acceptance reports `accepted` (and `queued` when applicable), `rejected`, `unknown`, or `not_sent`. A configuration failure—including a busy-setting rejection—prevents that call's prompt from being sent, but does not roll back settings already applied or remove the created session. A send failure leaves the configured session. Agent-send admission is rechecked against authoritative live membership after configuration and again after asynchronous runtime promotion; a completed close rejects later delivery without rolling back durable creation or configuration. Missing acknowledgements remain unknown unless existing operation evidence resolves them. Worker acknowledgement deadlines and unconfirmed durable sender attribution report message `unknown`, not a definitive rejection, even if the recipient is already running. Model/reasoning and prompt-toggle worker acknowledgement deadlines likewise report configuration `unknown`, and the optional prompt is `not_sent`. Combined create/configure/send is not atomic and is never automatically replayed. `operation.status` inspects retained operation evidence, including the separate phase outcomes, without executing the action again; a fresh create request with a new request key is a new create. The tool generates a timestamped request key before sending a mutation and includes it in the result or lost-acknowledgement error. Receipts are caller-scoped and retained only for the coordinator lifetime, subject to bounded storage; missing receipts report unavailable, never not-executed. Pending receipts are not evicted. Oversized receipt detail is explicitly marked `evidenceUnavailable` rather than silently discarded or treated as success. Stale or already-used keys cannot execute another mutation. Cancellation rejects the worker request but does not roll back an already-admitted coordinator operation; late results are dropped by request identity. A thrown transport/cancellation error for create, message, settings update, or close reports tool-level `outcome: unknown` and warns that the operation may continue: do not automatically repeat the mutation. Local validation and acknowledged rejections retain their known-failure behavior. Failures and incomplete phase outcomes use the SDK's thrown-tool error path; structured phase evidence and lookup keys remain in the model-visible error text.

For every cross-session message, including `create.prompt`, the coordinator derives sender identity from the calling worker, adds the sender identity/title (when assigned) and identity-bound `replyReference` to the recipient's model input, and publishes an Agent-attributed user-role transcript row with an Agent/bot cue. A send rejected before acceptance removes its optimistic row. The owning worker attaches authenticated sender provenance to the SDK user message at its durable append boundary; reload reads that embedded metadata (legacy `pie.agent-message-provenance` sidecars remain readable). Transcript display removes exactly one canonical sender envelope only when it matches validated persisted sender metadata, retaining attribution separately; durable model input is unchanged. This keeps the SDK echo comparable to its optimistic Agent row without showing the model-only envelope as message text. Unprovenanced or mismatched lookalikes remain user content. An idle send does not report accepted until its user entry has been persisted. The initial SDK user `message_start` preserves the direct request's attribution, including when a follow-up is already queued; only a later queued delivery consumes that queue's identity. On a fresh session the worker explicitly writes the buffered SDK entries at the user append boundary rather than waiting for the first assistant response; this is message acceptance, not answer completion. Queued acceptance acknowledges only enqueueing, not durable delivery; attribution travels with the user entry and is checked at delivery. If provenance cannot be confirmed after admission, the operation is partial/unknown and emits an ambiguous operational error rather than claiming durable success. `replyTo` resolves that stable sender identity only while its original session is live; it is not a title alias, operation token, or cross-host address. Title reuse never redirects it. Attribution does not create an automatic reply obligation.

There is no agent-facing `stop` action. `close` is the stop-and-close action. It admits any explicitly targeted live session, not just sessions created by the caller. New execution is fenced once closing starts. Pending agent prompts retain their pre-configuration cancellation generation through runtime promotion; closing invalidates it even if the same durable session is later reopened. A fresh request after reopening is admitted normally, and unrelated session changes do not invalidate that generation. Closing another session waits for confirmed host stop/cleanup or reports failure/unknown. Self-close returns `closeRequested` only after the host accepts responsibility; host cleanup is handed off after the response so the caller can stop without claiming close completion. Repeated closes join the owning operation. A hidden running target still uses stop/cleanup. When no tab or hidden running target exists, retained history alone cannot prove completion: the host requires a matching successful prior close barrier and no newer live/pending state, otherwise it reports unknown. A close of a pending create cancels queued sends; a late durable create is cleaned up, not reopened. Ordinary close retains on-disk history unless the session is private, and removes live addressability; explicit delete and private-session close use the existing irreversible deletion path. Cleanup preserves those same privacy semantics.

Transcript reads use one character-budgeted workflow for both lightweight checks and detailed inspection. The budget includes response metadata and the activity header; characters are UTF-16 code units, with boundaries kept clear of surrogate pairs. Renderer/accounting/debug metadata, duplicated mirrors, SDK result `details`, and image base64 are omitted. Explicitly included tool inputs/results share the same budget and can be paged within an entry rather than permanently cut to a preview. Completed messages provide stable content; live activity is separate and does not establish task completion.

Read cursors bind the session identity, content history, and projection options internally. They retain independent older/newer coverage edges and within-entry positions so increasing a budget or changing direction does not repeat already returned content. Ordinary appends preserve coverage. Changing inclusion options requires a fresh read; replaced history or a different session behind a reused title invalidates the cursor explicitly. An empty page must not promise inaccessible older content.

Message decisions, blockers, interface changes, and final findings; omit routine progress and acknowledgements. Prefer cheaper subagents for large-output inspection; use bounded reads for small checks. Before cleanup, check for owned sessions the user is still using; close sessions individually if any should remain open.

Queued steering/follow-up delivery keeps the active tool/skill selection without another skill-pruning prepass, regardless of whether the message came from a user or an agent. An idle-session request, including `create.prompt`, uses normal pruning. There is no agent-origin bypass. See [tool and skill selection](../../harness/tool-and-skill-selection/README.md#integration).
