# pie State Contract

## Session Selection

- The host store owns selection through `activeSessionPath`.
- `activeSession` in the webview snapshot is derived from `activeSessionPath` plus the current session summaries.
- `session.create` and `session.open` carry a `selectionToken`.
- `session.opened` may only activate a tab when its `selectionToken` still owns selection.
- Stale `session.opened` payloads may refresh cached data, but they must not steal focus. The host tracks current-generation durable-snapshot knowledge separately from execution-runtime readiness. Selecting an already-open tab with a known durable snapshot uses a host-local selection fast path and explicitly supersedes older selection-token ownership, even when that snapshot is cold. After backend restart both knowledge sets are empty, so the next selection performs `session.open` rehydration.
- A superseded selection request retains responsibility for operation cleanup,
  but its timeout/rejection is silent: only the current selection owner may
  replace the global notice or choose a fallback tab.
- Every actual host-local selection transition sends the runtime-free
  `session.viewed` RPC with the host-observed predecessor. The host changes the
  visual selection synchronously and does not await this notification. The
  backend records the viewed path and browse-time predecessor without opening
  the transcript or creating services; same-path reselection is a no-op. A
  notification failure never rolls back selection, is logged, and surfaces a
  notice only while that failed target remains current. A monotonic backend
  view fence prevents a slower `session.open` durable read from committing its
  viewed path after a newer local transition.

## Session Routing

- Mutating backend requests require an explicit `sessionPath`.
- `message.send`, `message.edit`, `message.continue`, `message.compact`, `message.interrupt`, and `session.truncateAfter` never fall back to the viewed or active session implicitly.
- Session-scoped backend events must include `sessionPath`.
- Missing `sessionPath` is treated as a protocol defect.

## Authoritative Session Activity and Capabilities

- The backend owns one billable-activity classification for each hot session. It includes an active request or extension command, SDK streaming, compaction/branch summary, retry/backoff, bash execution (including pending bash messages), and queued steering/follow-up messages. Busy snapshots, Stop eligibility, send/continue/compact/model/truncate guards, and runtime replacement/cleanup use that classification rather than independent approximations.
- SDK `agent_end` closes only the current low-level attempt. It does not clear the request or publish idle because post-run compaction, retry, queued continuation, or tool/bash activity may follow. The pinned SDK `agent_settled` event is forwarded explicitly through worker IPC as `agent.settled`; only that boundary finalizes request ownership and publishes settled capabilities. Confirmed worker loss synthesizes the same settlement before its final idle event.
- `session.opened`, `busy.changed`, and `agent.settled` carry backend-classified `SessionCapabilities`: `billableActivity`, `canContinue`, `canInterrupt`, and `canCompact`. The host stores these in the path-keyed `capabilitiesBySession` record. Pure host projection overlays the current non-terminal reducer-owned operation as optional `primaryOperation` (`operationId`, kind, phase, attempt, commit evidence, and recovery action) and exposes the result as `ViewState.sessionCapabilitiesBySession`; the backend never originates host operation phase. Pending create/duplicate paths fail closed for continuation and compaction while preserving the existing queued-send behavior. Hiding a running tab preserves the entry, while full session eviction removes it.
- `canContinue` is classified from the backend's complete SDK message context (or the complete durable cold-session context), never from the bounded transcript transport window. The webview is a passive capability consumer: an empty submit offers continuation only when the active session's projected `canContinue` is true.
- Capability snapshots fail closed for continuation. Billable activity implies `canInterrupt:true`, `canContinue:false`, and `canCompact:false`; idle sessions may compact, and only the backend interruption classifier may enable continuation.

## Backend Failure Recovery

- Backend JSONL records share a 32 MiB byte limit. An overlong correlated stdout response is replaced before writing with a `RESPONSE_TOO_LARGE` error carrying the same request ID, so the stream remains synchronized and the backend stays available. An overlong stdout event remains a fatal transport fault. Overlong stdin records are discarded through LF; when the bounded preview contains a request ID, the backend returns a correlated `REQUEST_TOO_LARGE` response. Subsequent requests remain readable. Session snapshot producers use a stricter 30 MiB budget and measure the complete final serialized event/response envelope, including LF, before writer enqueue. If metadata plus one required durable row cannot fit losslessly, transcript-page RPCs fail with typed `SESSION_SNAPSHOT_TOO_LARGE` rather than relying on writer overflow replacement or fatal event handling. A `session.opened` producer instead emits a bounded snapshot marked `snapshotUnavailable`; it first retains all ordinary metadata and drops only transcript/checkpoint bytes, with a final metadata-independent identity/lifecycle fallback if metadata itself exceeds the bound. That final fallback never retains user session names, model catalogs, model settings, prompts, reviews, or usage; its required summary fields use fixed placeholders/caps, and path/session identity, lifecycle, selection, and live-recovery strings have fixed UTF-8 bounds, guaranteeing the complete event envelope remains below the producer budget. The durable row is not truncated, any loaded host window is preserved, and the committed create/duplicate/truncate acknowledgement remains successful.
- Intentional stops do not produce public unexpected-exit events, but an intentional stop during startup still rejects that child’s readiness promise. Process generations prevent an old exit from clearing a replacement. Backend restart is manual; there is no automatic restart. Manual restart projects `backendReady:false` before its first await, drains already-accepted model/reasoning/preference writes, then closes backend stdin and waits for accepted requests to settle before starting the replacement generation. The settings file lock records its owner PID so a replacement also recovers immediately from a hard-killed owner rather than remaining unusable for the stale-lock window.
- Provider header waits are bounded per provider. Two consecutive header stalls open a shared transport circuit, so sibling sessions fail locally instead of consuming every provider slot and timeout budget. After an exponentially backed-off cooldown, exactly one half-open probe may reach the provider; response headers close the circuit, while a failed probe reopens it. User cancellation never counts as provider failure. The circuit survives live concurrency-setting changes and is exposed through provider capacity/metrics.
- Provider admission, response-header wait, and body-idle wait are finite, individually capped at five minutes, and correlated to the exact request. Queue value zero means the five-minute safety maximum. Typed provider rejections preserve retryability and HTTP status across worker IPC; transport success is not observed until no-body completion or clean body EOF. Host/backend model-start deferral requires that exact request to be provider-pending and never extends beyond the cumulative twenty-minute ceiling.
- Affected session paths are deduplicated. Crash cleanup materializes each host-owned live turn as interrupted, preserves only durability-confirmed terminal tools, interrupts queued user messages, and clears pending extension-UI, retry, wait, interrupt, checkpoint, and queued transient state even when no transcript is loaded.
- The short exit notice contains the interrupted-session count and reliable activity classification; credential-redacted stderr is exposed only as `noticeRaw` with `noticeKind: backend-exit`.

## Session Cleanup

- Closing an **idle** session or invalidating a session clears durable transcript cache, `LivePipelineState` turn/tool/pending-owner/tombstone state, alias state, current-turn correlation metadata, busy dedup state, pending composer inputs, and queued per-session operations.
- Privacy mode is session-scoped and surfaced as `ViewState.privacyMode`; its marker is persisted only to survive a host restart, never as session content. While enabled, run analytics are suppressed and any existing analytics are scrubbed. Billable-invocation records remain process-local so the live private tab can display usage, but they are never appended to disk or included in exports; enabling privacy rewrites away already-persisted rows and closing the private session scrubs the in-memory rows. Closing a private session retires the backend runtime, removes the transcript/system-prompt sidecar and review sidecars, clears analytics/export/checkpoint records, and only removes the privacy marker after deletion succeeds.
- Closing a **running** session is a tab hide, not session cleanup. It removes and persists the tab selection only; live transcript/tool state, pending ownership, running markers, composer/file state, backend work, and current-run analytics remain recoverable. Repeated/stale close commands for an already-hidden tab are no-ops, and renderer close interactions carry a bounded interaction identity in addition to the existing view-generation fence.
- Closed sessions remain discoverable through the session-history menu. Hidden running sessions sort before idle history, retain an explicit Running badge, and reopen through the ordinary authoritative `openSession` command rather than a webview-local shortcut.
- A webview ready handshake restores a running session absent from the persisted open-tab list only when its absence has no host-owned intentional-hide intent. This repairs an accidental renderer-reload omission without pretending that a full extension-host restart can preserve an in-process backend. Both ordinary user closes and review-closure hides (closeReviewed/closeSelf) record intentional hide intent, so the handshake must not resurrect either; the marker (`intentionallyHiddenRunningPaths`) is host-owned, survives the webview reload boundary, and is pruned when the session is explicitly reopened or no longer running.
- V2 review closure actions are durable outbox commands, not review writes. `closeReviewed` is allowed for an already-reviewed running session (a tab hide) while evidence and review recording remain forbidden for running targets; `closureEligible` reflects this (non-self with a persisted canonical production review). An idle target reaches `succeeded` only after correlated close cleanup and tab persistence both succeed; a running target remains live and reaches `succeeded` after its tab-hide persistence succeeds. Failures append retryable state, and a crash before the fsynced terminal append leaves the prior pending/retrying action authoritative. A still-failing action becomes terminal `failed` after a bounded number of attempts (`MAX_CLOSURE_ATTEMPTS`); the durable `failed` status prevents reclaim on later refreshes, while a crash before the terminal append leaves the prior retrying record authoritative so crash reclaim/retry semantics are preserved. Drain reconciliation runs unconditionally on every backend startup/restart and uses both `fs.watch` as a low-latency hint and a bounded sidecar-fingerprint poll as the missed-event recovery path. Reusing an active pending/retrying action appends the same action ID as a durable wake record; catalog-absent active targets with a captured path are exposed as synthetic summaries so they enter the normal idempotent close/persist lifecycle instead of remaining silently pending.
- Pending composer inputs are session-scoped host state: close/invalidate clears them for that session; extension restart/shutdown clears all remaining pending inputs.
- Pending-session placeholders are cleaned up one session at a time; overlapping creates must not share teardown.
- Pending session identifiers must be collision-safe under rapid repeated creation.

- The open-tab registry consumed by worker extensions is the host's complete current snapshot, not inherited process environment. Open/close/pin changes and accepted `BusyChanged` transitions publish immediately through a monotonic coordinator→worker sync domain; newly promoted workers receive and acknowledge the retained snapshot before runtime readiness. Live broadcasts target only ready workers. A missed live acknowledgement does not retire an executing worker: publication returns without waiting and the newest registry revision retries with bounded backoff. `PIE_OPEN_TABS` remains the compatible JSON array and `PIE_OPEN_TABS_REVISION` is its worker-sync revision fence. Retries reuse the host source revision, older publications cannot roll back newer membership or flags, and unchanged snapshots are force-resubmitted only across backend startup/replacement.

## Snapshot Recovery

- Worker-sync retries at an equal revision are accepted only when the bounded payload fingerprint is identical; they join the original apply or replay its acknowledgement. A changed equal-revision payload is a fatal protocol fault. Reloadable control-plane broadcasts receive a 30-second acknowledgement grace; the auxiliary open-tab registry remains nonfatal and retries the newest revision with bounded backoff.
- Full snapshots are the authoritative base.
- A full snapshot contains the currently loaded transcript window (`transcript`) plus explicit window metadata (`transcriptWindow`), not necessarily the entire historical transcript. Session token/cost accounting is carried separately as a whole-branch `sessionUsage` projection of the host-owned billable-invocation ledger; loading, culling, switching transcript windows, or restarting the host must never reduce or duplicate the displayed cumulative metrics. Backend transcript usage is migration/rebuild input only and is never merged with an existing ledger projection.
- `initialContextEstimate` is additive state separate from provider `contextUsage`. Before any user message or provider usage, an empty `runtimeReady:false` session may carry a fresh estimate of every successfully discovered/registered prompt, tool, and skill before Pie runtime filters. Here “all configured” excludes missing/uninstalled packages and resources excluded by Pi resource settings because those resources were not discovered as runnable registrations. A one-shot isolated worker obtains the catalog from normal unfiltered hot semantics (`_originalSystemPromptOptions`, all `getAllTools()` names with their real prompt snippets/guidelines, and extension `resources_discover` contributions). It builds the complete system prompt once from those all-tool inputs and loaded custom/append/context/skill metadata, then adds every registered tool description/schema once; provider-hidden instructions, prompt-template bodies, and full skill bodies remain excluded. The worker uses an in-memory session, starts with Pi/npm/yarn package and startup networking forced offline, installs an outbound-fetch and turn-producing-method deny boundary before extension `session_start`, and invalidates the inventory after even a caught network attempt so a partial provider-discovery catalog is never published. Provider-catalog refresh hooks skip this inventory mode. The child is disposed and process-tree-cleaned, with process-tree fallback if Windows guardian termination fails, and is neither used during internal promotion nor promoted/cached. Failure/timeout omits the estimate. Its token numerator is model-independent; while cold, the currently selected model’s context window is always the denominator and the worker-reported window is only a fallback. Any hot snapshot, user message, or provider usage supersedes it; the compact indicator has no approximation prefix.
- State-envelope revisions are **per renderer** and advance on each full snapshot for that renderer; they continue to detect host-instance counter resets in combination with `hostInstanceId`. Cross-renderer revision comparison is never meaningful: full snapshots make it unnecessary, and `hostInstanceId` still detects host replacement.
- Every envelope carries `protocolVersion` matching `WEBVIEW_PROTOCOL_VERSION` and the deterministic compile-time `PIE_BUILD_ID`. Readiness messages carry the renderer's compiled build id rather than echoing host data. A protocol mismatch is a terminal renderer boundary: the webview preserves its last compatible display while latching later inbound/outbound traffic off, and no receipt/commit evidence acknowledges incompatible state. Build identity is diagnostic at runtime; a same-protocol build mismatch continues routing and applying state so an in-place rebuild does not force a window reload or interrupt active sessions. Vite recomputes the build id on every watch emission before chunk hashing, and a one-shot build still fails if the emitted host/webview identities differ.
- Delivery evidence is split: `stateReceived` proves receipt, `appCommitted` proves the app tree committed, `transcriptCommitted` proves the signed displayed transcript leaves match the host expectation, and `paintObserved` records the next visible paint. Only a valid accepted-ledger `transcriptCommitted` identity advances transcript correctness.
- The semantic identity is bounded-cost and computed from the projected `TranscriptView`: durable rows joined with the host-owned active turn/tool records. It signs the last three transcript leaves plus bounded live/terminal tool aggregates. Queued follow-ups cannot push an active owner outside the signed live-tool aggregate.
- Transcript virtualization may defer tool-card component materialization only for completed messages older than that signed three-message tail. Lightweight placeholders preserve scroll geometry until a historical card approaches the viewport; streaming, queued, and signed-tail messages retain complete leaf evidence. Switching sessions preserves the transcript host/surface but resets the session-owned virtualizer at the bottom. A user-requested bottom jump re-snaps through a bounded delayed-measurement window and cancels as soon as manual scroll ownership resumes.
- Ordinary state transport is snapshots-only. Full snapshots carry the complete compact `ViewState`; ordered assistant `parts` are authoritative, so the renderer projection omits the redundant legacy `toolCalls` mirror whenever those parts already carry tool calls (legacy-only messages retain the mirror). Streaming delivery remains latest-wins and uses a slower bounded cadence for very part-heavy transcripts, preserving interaction windows while retaining full-snapshot authority. Large tool results, recursive subagent transcripts, and reasoning bodies are represented by bounded `LazyDetailRef` metadata rather than inline content. A separate bounded detail-response imperative loads content from the durable backend transcript (or current host-owned live state): generic tool/reasoning bodies request it on expansion. Live-addressable subagent children use the Phase 5 page-backed detail subscription instead: a collapsed card renders only its bounded compact preview and never subscribes; explicit or automatic expansion sends exactly one `detail.subscribe` (carrying the current `viewGeneration`, stable `detailKey`, webview-minted monotonic `detailAttempt`, and immutable `address`); every returned frame echoes that attempt so even a pre-start frame from a retired owner is ignored; collapse — including during the close animation — immediately discards the heavy pages/value/measurements and sends `detail.unsubscribe`. Re-expansion before the unsubscribe is acknowledged mints a new owner and ignores frames bound to the retired subscription. Baseline pages, deltas, rebases, terminal handoffs, and errors are explicit key-scoped states; the complete serialized detail is never retained (pages are a bounded, visibly-pinned LRU transport cache and the renderable value is derived per record), so evicted or gap ranges are re-fetched through `detail.fetchPages` and legacy non-addressable refs keep the generic one-shot path. Terminal and cold detail are served by the coordinator's paged durable authority: `detail.subscribe`/`detail.fetch` are routed to the owning worker while the live source exists, and to the backend durable store afterwards — which resolves the exact terminal tool result from the durable JSONL by its stable tool-call id and producer lineage, segments it into exact UTF-8-safe, checksummed pages, and streams `detail.start` (including the exact byte and Unicode-code-point manifest totals) → ordered `detail.page` → `detail.terminal` (a live `NOT_FOUND`/`NOT_LIVE_ADDRESSABLE` subscribe falls back to this durable path for the same subscription id). No single response in this path ever approaches the 30 MiB transport ceiling, so details far larger than 64 MiB remain retrievable; the generic bounded one-shot `session.loadDetail` preview path is unchanged. A lazy subagent must render directly as that collapsed preview card and then toggle only between collapsed preview and expanded transcript; it must never first degrade to a generic tool row. Loading/rebasing/failure/retry/unavailable/stale states are explicit; in-flight requests are deduplicated and loaded details use bounded LRU caches on both sides. Detail subscriptions are key-scoped so one response does not re-render unrelated visible cards. Detail responses are not copied into every later full snapshot, and cache eviction/reload only requires re-fetching from the lossless durable source.
- When the view is hidden or not ready, the host marks globalDirty; the next flush emits a full snapshot.
- When visibility returns, the next host-to-webview sync is a full snapshot.
- The webview clears overlay/transient UI when the host instance changes or the active session changes.
- Active text, reasoning, reply model/provider/reasoning-level metadata, tool-call drafts, typed bounded previews, tool lifecycle, producer phase, sequence, and extension-UI ownership live only in host `LivePipelineState`. `ArchState.transcript` is the durable history cache, not a second live authority. Projection purely joins the two. Active tool drafts are an ordered multi-draft `Record<toolCallId, LiveToolCallDraft>` plus first-observation placeholders in `LiveAssistantPart`; there is no singleton current draft. Each draft has a stable provider tool-call ID, name, raw `argumentsJson`, and explicit `drafting`/`ready` phase. Per-draft and aggregate UTF-8 byte bounds apply independently.
- Agent reply headers derive the request time from the preceding delivered user message's `createdAt`; queued follow-ups do not take ownership until delivery. If that user message is outside the loaded transcript window, the header omits the request time rather than substituting the assistant start time.
- Backend semantic envelopes use live protocol **v7**, independently of the RPC transport wire version. They are monotonic per turn/attempt; version skew, missing, rejected, illegal-owner, or out-of-order events trigger rejection or the effect-owned `liveTurn.checkpoint` RPC. Provider `toolcall_start` creates one keyed draft and inserts its ordered part placeholder, `toolcall_delta` appends the raw JSON fragment without parsing it, and `toolcall_end` marks only that draft `ready` while replacing its text with the SDK's full finalized argument serialization. `ready` means provider generation ended, not that input validation or execution succeeded. Duplicate boundaries are idempotent; malformed, oversize, ownerless, or post-abort observations follow the normal rejected-observation/checkpoint recovery path. Tool progress establishes an initial JSON-safe preview snapshot and then carries restricted structural patches (`set`, `delete`, string append, and array append) with both turn `baseSeq`/`seq` and per-tool progress revisions. The backend retains the complete assembled canonical preview; identical cumulative SDK updates consume no sequence and emit nothing. The host applies a patch only to its declared base revision and otherwise enters gap reconciliation. Checkpoints are structurally validated, recovery-only, and in-memory. The backend maintains a canonical conservative byte total incrementally across JSON escaping, every text/reasoning part and draft, tool inputs/metadata/previews/terminal results, collection syntax, and the structural envelope; an observation is rejected before its complete active checkpoint could exceed 30 MiB, leaving 2 MiB of JSON-RPC/record headroom under the shared 32 MiB ceiling. Semantic envelopes and `LiveTurnRecord` carry that total. The progress patch hot path trusts the backend total and never stringifies the reconstructed large preview; checkpoint recovery serializes once and verifies actual bytes against the cached total. Checkpoints contain every current draft and the complete currently assembled representable live state and impose no total tool-count limit. Older durability-confirmed tool input/result payloads are semantically compacted in backend repair state while lifecycle identity and a detailed recent tail remain. Applying such a checkpoint preserves richer matching terminal details already held by the host. Terminal lifecycle watermarks expose a lost final event. A completed checkpoint attempt releases its runner dedupe key before the synchronous result dispatch, so a reducer-requested retry cannot be suppressed as the still-completing prior attempt. Repeated repair failure interrupts locally and never replays tool execution.
- Tool execution end and durable terminal are separate monotonic boundaries. The SDK `tool_execution_end` observation emits transient `tool.executionEnded` before the following `turn.phase`, carrying only the completed/failed status and measured duration. Projection uses `terminal ?? executionEnd` for status/duration and `terminal.result ?? preview` for result, so one completed sibling loses its spinner while other sequential/parallel siblings continue running. `executionEnd` is not durability evidence: only a matching persisted toolResult upgrades the same record to `tool.terminal`; conflicting or regressive progress/end/terminal observations are rejected. Only durability-confirmed terminal tools enter settled-history compaction, survive restart interruption, or contribute durable result metadata. An unconfirmed execution-ended call remains checkpoint-recoverable during the live process but is dropped on restart.
- Tool and assistant terminal envelopes are withheld until the patched SDK append returns a stable session-entry ID. Aggregate completed-tool count or payload size does not abort a healthy turn; individual semantic records remain bounded. `tool.started` promotes/removes only its matching draft and reuses that draft's ordered part; sibling drafts remain active. The reducer atomically appends the durability-confirmed terminal message and removes its live turn/tools/drafts. Before replacement it reconciles durable calls by tool-call ID, carrying only safe live render metadata (including `parallelGroupId`, execution identity, and timing when absent) into both ordered parts and the legacy `toolCalls` mirror. The host also projects the turn's canonical message ID as optional `ChatMessage.renderIdentity` on both live and reconciled durable rows; this field is non-authoritative and is used only for UI keys and scroll anchoring, while durable `id`/`durableEntryId`, editing, detail retrieval, commit evidence, protocol semantics, and transcript ownership remain unchanged. Durable name/input/result/status remain authoritative, and unmatched drafts are never materialized. A fresh session branch wins on reopen; dangling persisted work is shown as interrupted with every unconfirmed draft removed.
- A busy `session.opened` refresh carries a bounded authoritative live-turn checkpoint atomically with its durable paging state. The host replaces stale/tombstoned state for that session from the checkpoint before projection. An authoritative idle open with no host-owned optimistic run clears any orphaned live turn/tools, pending owner envelopes, terminal tombstones, current-turn correlation, and extension-UI ownership for that session before projection; the durable tail must never render beside a stale active copy. Every `session.opened`, `session.preload`, and transcript-page snapshot is fitted at its complete final JSONL envelope shape. On overflow the backend first omits the live checkpoint and rebuilds from the normalized durable transcript, then removes whole rows away from the pinned/requested edge while preserving exact `totalCount`/`loadedStart`/`loadedEnd` and derived gap flags. Individual durable rows are never truncated. If a checkpoint cannot be represented, the backend keeps the durable assistant tail visible and the host requests repair; the open retains `liveTurnRecoveryIdentity` (`turnId` + `attemptId`) so even a cold host with no prior `LiveTurnRecord` can address `liveTurn.checkpoint`. If no required durable row can fit, `snapshotUnavailable` makes the metadata-only/gapped transcript explicit, preserves an existing loaded host window, and surfaces a bounded notice. A busy open must never hide durable work merely because live recovery is unavailable. When an authoritative durable assistant row replaces an already durability-confirmed row (matched first by `durableEntryId`, otherwise exact durable message `id`), the host carries forward only `renderIdentity` and missing matching-tool render metadata (`parallelGroupId`, `executionId`, `startedAt`, `durationMs`, `seq`). Incoming content, name, input, result, status, and unmatched calls remain authoritative, and ordered parts stay synchronized with the legacy mirror. Webview reload restores the same host state through the next full snapshot.
- History compaction is surfaced as first-class UI state, not inferred from the transcript. The backend emits `compaction.started` when the SDK's compaction LLM call begins (alongside the busy re-arm) and `compaction.ended` when it finishes (success, failure, or abort), carrying the SDK's `reason`, an explicit `outcome` (`succeeded`, `failed`, or `aborted`), and `occurredAt`, plus `tokensBefore`/`estimatedTokensAfter` only when a result was produced. Manual compaction always uses reason `manual`; its start/end events also carry the stable operation identity and acknowledgement attempt, and only the first matching end observation applies its terminal outcome. The host tracks `compactingSessionPaths` (always a subset of `runningSessionPaths`; pruned by `RunningSessionsChanged` and session eviction) and a per-session `lastCompactionBySession` chip record that expires after a bounded TTL via the `ClearLastCompaction` effect → `LastCompactionCleared`. `session.opened` carries `isCompacting` so a session opened mid-compaction restores the indicator; compaction emits no `message_start`/`message_end`, and manual or post-agent compaction may run while `isStreaming` and `activeRequest` are both false. Threshold compaction never manufactures agent work: when a tool or queued turn already requires another provider call, the SDK refreshes that natural continuation with the compacted context; after a completed terminal response, history compaction settles without a zero-prompt call and the agent remains finished. Provider-forced overflow compaction is resumable because the provider response failed: this includes an empty `length` response whose usage counters are all zero when the SDK's last-valid-usage estimate remains at least 98% of the model window. The failed assistant row consumed by recovery is omitted from rebuilt provider context and transcript projection, so reopen, duplicate, edit/truncate replacement, and worker promotion cannot reintroduce a row the live retry never saw. If the bounded retry itself overflows, that tail is projected as interrupted and explicit Continue removes it, resets the bounded overflow attempt, and enters the same zero-prompt lifecycle. The webview renders a live "Compacting…" activity row + toolbar chip and a transient "Compacted · freed N tokens" success chip only for a succeeded outcome; failed and aborted outcomes clear activity without claiming success, and the compaction trigger swaps to a spinner while compacting.
- The delivery controller retains one unsettled post and at most one accepted-but-uncommitted revision. New host state is lazily coalesced behind that commit gate, because `webview.postMessage()` acceptance does not prove Chromium consumed or rendered the snapshot; allowing streaming posts to outrun transcript commits creates a stale renderer queue that catches up only after the agent stops. Settlement and commit are timed independently. An explicit user session selection is the bounded exception: it may retire the older accepted streaming revision and post the latest selection snapshot immediately after any unsettled post resolves; ordered delivery is preserved and evidence for the retired predecessor is stale telemetry. When the renderer explicitly reports `transcriptCommitBlocked` and newer host state is already coalesced, the controller retires only that stale acceptance and immediately posts the latest desired snapshot; a block with no newer host state leaves the commit deadline intact so a stable render defect still receives bounded recovery. This prevents active text/tool streaming from turning repeated leaf mismatches into a webview reload storm. A post-settlement timeout retires its posted revision before retry, just as commit-timeout recovery retires accepted revisions, so late `stateReceived`, `appCommitted`, `transcriptCommitted`, and paint evidence is stale telemetry rather than a future/unaccepted protocol defect. Recovery resnapshots the latest desired state before bounded reload escalation. Reload does not discard host-owned live work. Only a Preact component failure is fatal renderer evidence; global `window.error`/unhandled-rejection events remain bounded diagnostics, and Chromium ResizeObserver loop notices are explicitly nonfatal. The per-renderer reload circuit uses a rolling wall-clock window that transcript commits cannot reset, so a reload → commit → repeated-error cycle is throttled until enough prior attempts age out.
- **A stale `webviewReady=false` belief self-heals via `WebviewReadinessProbe`.** `canPostSnapshotToView()` gates posting on `hasView && webviewReady`, and `webviewReady` is the host's *belief*: it flips `false` on every webview reload (asset-version mismatch, hot reload, watchdog force-reload) and is restored only by an inbound `ready`/`refreshState` reaching the readiness setter. If that handshake does not restore it (a lost `ready`, or an asset-version reload loop whose handshake is consumed by the mismatch branch before the setter), the host marks `globalDirty` and posts nothing indefinitely — the agent advances host-side while the webview freezes on its last frame, recovered only when the user refocuses. The probe breaks that stall: while the view exists, readiness is believed false, and state is dirty, it periodically pushes the pending snapshot directly and adopts `postMessage`'s `delivered=true` as the readiness signal. Bounded by `READINESS_PROBE_MAX_ATTEMPTS`; a genuinely-unresponsive webview is left to the watchdog force-reload / visibility transitions. The probe's reload-skip is time-bounded: it bails for the first few ticks of a genuine reload (don't post to a renderer being replaced) but, past `RELOAD_STUCK_SKIPS` consecutive skips (~6s), treats `reloading` as stale (a reload loop whose every `ready` is consumed by the asset-mismatch branch, or a lost `ready` from a renderer that never finished loading), force-clears it, and probes — otherwise the bail would trap the probe forever (`attempts` never increments on a reloading-skip) and, with the watchdog force-reload throttled rather than suppressed while streaming, leave the webview stuck for the throttle window until the probe self-healed it.

## Conserved Billable Accounting

- `StatsService` owns one append-only `billable-invocations.jsonl` ledger per workspace analytics store. `invocationId` is the idempotency key; exact duplicates are ignored, conflicting reuse is rejected, malformed/torn replay lines are skipped, and immutable rows are replayed before projections are served.
- One row represents one observable billable provider invocation. Kinds are `conversation`, `retry`, `history_compaction`, `branch_summary`, `skill_pruning_prepass`, `session_title`, `subagent`, and `other`. Rows correlate session/path/branch plus parent operation, run, and tool where available; provider and model are always explicit, using visible unknown sentinels when an adapter cannot identify them.
- Token channels, provider totals, reported cost, catalog calculation and rate snapshot, timing, and outcome are immutable settlement evidence. Provenance is `exact`, `estimated`, `unpriced`, or `unknown`. An observable call with unavailable usage produces an explicit instrumentation-gap row; unknown values are absent rather than invented zeroes.
- Every durability-confirmed conversation provider response, SDK retry attempt, compaction/branch-summary stream call, skill-pruner scorer retry, title call, and terminal subagent attempt dual-writes the ledger and legacy run analytics. Conversation terminals are only a compatibility fallback when no per-response settlement was observed. Historical transcript/run usage may seed deterministic migration rows only when no ledger evidence covers that durable source/run.
- Session UI, aggregate token/cost stats, and explicit/automatic analytics exports project ledger rows. Cost uses provider-reported values first, otherwise the immutable catalog version/rate snapshot captured at settlement. Unknown/unpriced provenance remains visibly incomplete. Working time is not derived from token/cost rows: `WorkingTimeService` continues to project the separately persisted correlated run activity timeline.

## Execution Ordering

- Lifecycle requests (`create`, `open`) are serialized through a host lifecycle queue.
- Session mutations (`send`, `continue`, `compact`, `edit`, `truncateAfter`, `interrupt`) are serialized per session path.
- Backend send, empty-continuation, and title requests join an in-progress runtime replacement through one bounded transition wait. The wait yields between stale-owner checks, returns a typed ready/timeout outcome, and a timeout rejects with `SESSION_TRANSITION_TIMEOUT`; an immediately resolved stale context cannot spin or starve the deadline.
- `message.interrupt` is a stable, idempotent operation and a bounded abort-completion barrier. Its coordinator-owned ledger joins concurrent retries and replays one terminal result. While its registry record is non-terminal, `runningSessionPaths` and projected `primaryOperation` keep the composer in `Stopping…`; submission is blocked so stop→send cannot enter the dying turn. Completion covers active generation, queued prompts, retries, history compaction, branch summaries, bash/tool work, and every other window in the backend billable-activity classifier. If cooperative teardown does not make that complete classifier idle, the supervisor force-kills the worker, confirms process exit, revokes write/network authority, and returns a forced-recovery terminal. Interrupting an already-idle session is a successful no-op.
- A successful interrupt terminal installs `retiredEventFence` on that reducer-owned operation record. Late `busy=true`, `session.opened{busy:true}`, stream, or live-semantic publications from the retired turn cannot re-arm activity or mutate history; the next genuine Send/Edit/Continue/Compact command clears the registry fence before optimistically starting work.
- An empty composer submit is a first-class interrupted-turn continuation, not an empty user prompt. The webview exposes it when the latest conversation-owned tail is an interrupted assistant, a delivered user with no assistant response, or an assistant whose folded tool results have no following provider response. The host dispatches `Continue` without an optimistic user row, registers a stable operation before effects, and routes `message.continue` through the same per-session mutation FIFO and generation-scoped backend idempotency authority. The SDK adapter accepts both interruption shapes: it removes a trailing aborted assistant from provider context, or resumes directly when interruption happened before the next provider message and context therefore still ends at the triggering user/tool-result boundary. It retains durable history and enters the ordinary run lifecycle with zero prompt messages. It must not call `session.prompt()`, emit a user message, expand prompts, or run `before_agent_start` and its skill-pruning prepass. A completed assistant tail fails without starting provider work. If Stop or runtime replacement wins the acknowledgement-to-start gap, the backend emits a terminal `message.aborted` observation with explicit `cancelled` or `superseded` outcome and no `messageId`; a continuation rejection before `message_start` emits the same no-`messageId` terminal shape with outcome `failed`, so no older assistant row can be stamped as the failed attempt. A lost acknowledgement enters typed ambiguity and is reconciled by late lifecycle evidence, generation-scoped `operation.status`, or confirmed generation death without issuing another zero-prompt run.
- Editing has restart semantics. `EditRpc` sends one `message.edit` request carrying a stable `operationId`; the coordinator owns idempotent interrupt → authoritative-branch validation → atomic truncate → replacement send under one backend transition. The atomic transcript rename is the destructive commit point. A definitive failure before that point restores the exact removed tail and submitted inline editor. Stop marks an edit waiting in the host session FIFO cancelled before entering the backend, so it cannot begin a destructive transition after Stop has won. At or after the commit point, cancellation, acknowledgement loss, replacement failure, or generation death never restores obsolete history: capability projection remains `Saving edit…`/`Restarting…` while status reconciliation is non-terminal, then exposes the authoritative terminal recovery. A replacement-worker preflight or abort event carrying the edit's stable operation ID is itself post-commit evidence even if it outruns the coordinator acknowledgement, because that worker is promoted only after the rename. Backend death without a final status leaves commit evidence `unknown` and keeps the replacement authoritative; only an explicit `committed:false` result permits rollback.
- Optimistic UI writes must be reversible when the authoritative operation fails. A first send to a cold session receives the service-initialization pre-ack budget; hot sends retain the short early-ack timeout. Promotion failure is still pre-ack and follows ordinary optimistic rollback. The longer budget is conditional and does not weaken hot-send timeout detection.
- The EffectRunner routes session-scoped mutation RPC effects through `enqueueSessionOperation(sessionPath, ...)` to guarantee per-session FIFO ordering without holding the global lifecycle queue. Read-only `liveTurn.checkpoint` snapshots bypass mutation queues so recovery cannot wait behind the active work it is repairing. Checkpoint requests address the exact `sessionPath` + `turnId` + `attemptId`; while a queued-message handoff has both a terminal predecessor and a new active segment, repair must return the requested accumulator rather than whichever segment is newest. A slow prepass or interrupt for one session cannot block opening, creating, or interacting with another session.
- Lifecycle effects (`OpenSession`, `CreateSession`) use `enqueueLifecycle(...)` directly (no inner session queue). Model/catalog ownership fences are captured when the queued RPC actually starts, not when optimistic selection is created; create retries carry an attempt number so late publications use the exact attempt's fences.
- Pending create/duplicate tabs never issue backend reads or writes against pseudo-paths. Their model picker is seeded from the exact provider-qualified predecessor/default catalog and remains interactive while authoritative hydration catches up; opening a cold durable tab likewise borrows the last usable catalog until its own arrives. Model/reasoning choices made against a pending path, behind another model write, or while the backend is unavailable update the visible session badge immediately, coalesce per session, and remain host-owned until the target is writable. The reducer replays choices one at a time in original click order because `settings.set` also owns the global default; model-blocked sends wait for that session's write to settle, and backend loss rolls an accepted optimistic write back into this retry queue. Replay preserves capability checks, one-time image-removal confirmation, optimistic rollback, and model-write fences. A successful write requests fresh post-write hydration so a response-first create cannot strand a borrowed catalog. Catalog refresh never relabels an already-usable catalog as loading, late responses cannot recreate closed-session state, and the composer renders no additive loading chip beside the active model. Failed catalog discovery remains distinct from a successful authoritative empty catalog. Global settings and per-session catalog hydration use separate monotonic revision fences plus backend generation/model-write ownership, including `session.opened` snapshots.
- New unnamed sessions use the normalized, 40-character first-prompt snippet as their immediate replaceable name. When session-title generation is enabled, `ArchState.sessions.titleGenerationBySession` owns its `armed`/`pending`/`failed` lifecycle and `ViewState.generatingTitleSessionPaths` is projection-only spinner state. Pending-path replacement rekeys this ownership before backend work can start. The low-priority title RPC begins only at the first assistant-start commit point and runs outside the per-session mutation queue, so it never blocks chat. A result may replace the snippet only when its path/correlation fence still owns the pending attempt; explicit SDK/manual names are checked before inference and again before durable write and always win. Timeout, invalid output, rollback, close, or backend failure leaves/restores the snippet and clears the spinner without a blocking notice. See `docs/SESSION-TITLES.md`.
- `ArchState.operations` is the reducer-owned common operation registry and is a `Record` keyed by stable `operationId`. Create, duplicate, send, edit, interrupt, continue, and manual compact record operation kind, trusted serializable initiating source, pending/resolved/source session identity, causal parent and selection identity, owning backend generation, monotonic acknowledgement attempt, phase, acceptance, commit evidence, non-terminal recovery, and at most one terminal `{ outcome, reason, recovery }`. Terminal transitions are immutable: duplicate or contradictory terminal observations are no-ops, and a terminal ID cannot be resurrected with changed parameters. The interrupt retired-event fence also lives on its terminal registry record rather than in a parallel session collection. `SessionSummary.creationState` and `createOperationId` remain compatibility projections for the existing pending/delayed tab UI, not a second semantic authority.
- Create/duplicate operations carry one host-generated `operationId` across local transport timeout and explicit retry. A typed transport deadline enters the recoverable non-terminal `ambiguous` phase rather than failure; retry preserves the ID and prior commit uncertainty while incrementing `attempt`. A durable event from an earlier attempt may settle a later waiter for that same generation. Backend-generation death or a definitive pre-commit rejection terminalizes the operation once and rolls back only its pending path. A delayed tab exposes explicit retry while remaining closable; a hidden late success drains queued work but never steals focus or reopens, including after its queued send starts and the renderer reloads. The backend's generation-scoped `CreateOperationLedger` validates a canonical mutation-intent fingerprint before joining, retrying, or replaying an ID: create cwd and duplicate source/kind are immutable, while selection token and attempt remain transport metadata.
- Every production `message.send` mints one host-owned `operationId` at ingress and carries it unchanged through `Send`, queued/backend-ready ownership, `SendRpc`, coordinator→worker routing, `activeRequest`, queued-delivery correlation, lifecycle events, live semantic envelopes/checkpoints, and terminal registry evidence. It remains distinct from transport `corrId`, optimistic transcript `localId`, backend `requestId`, and semantic `turnId`/`attemptId`. The operation registry owns lifecycle truth; `pending.ops`/`pending.promoted` continue to own exact optimistic rollback snapshots.
- Generation-scoped backend operation ledgers key mutation execution by `operationId` plus a canonical kind-specific intent fingerprint. Send uses `{ kind, sessionPath, text, inputs, localId }`, edit adds its immutable target entry, interrupt uses `{ kind, sessionPath }`, continue uses `{ kind, sessionPath }`, and manual compact uses `{ kind, sessionPath, reason:'manual' }`. Edit and interrupt use coordinator-owned ledgers because they may deliberately retire their worker; ordinary message mutations remain worker-owned. Same-intent concurrent requests join and terminal retries replay their original result without repeating a truncate, provider start, compaction, or interrupt. Changed-intent reuse fails with typed `OPERATION_INTENT_MISMATCH`. Generation-addressed `operation.status` is read-only and reports pending, accepted (including destructive/semantic commit evidence), or a typed failed/cancelled/superseded/aborted terminal; it never starts or retries a mutation. The coordinator retains each worker-owned operation's exact owner for the backend-generation lifetime, so a retry or status query after worker replacement returns `SESSION_GENERATION_ENDED` instead of consulting a replacement worker's empty ledger.
- Send acknowledgement is distinct from send commit. A successful RPC marks `accepted`/`awaiting-commit`; the first correlated semantic or durable start/terminal boundary marks one immutable settled terminal. A local acknowledgement or model-start deadline marks `ambiguous` with reconciliation recovery and never rolls back by itself. The host reconciles via a correlated late response/event or a bounded, read-only `operation.status` poll; a pending/transiently unavailable status retries with bounded backoff, and exhaustion keeps the prompt in place, blocks another send for that session, and exposes an explicit backend-restart recovery action. Only definitive backend rejection, preflight failure, or confirmed owning backend-generation death may fail and roll back. Events/status from another backend generation are ignored. Queued follow-ups retain independent operation IDs and delivery state while accepted, settle only when their own delivery/start is observed, and receive one backend cancellation terminal (carrying both `operationId` and `localId`, independently of the clear/interrupt acknowledgement) when queue-clear or interrupt wins before delivery; a delivery that won the race remains the immutable settled terminal.
- `Log` executes directly without queueing. `PersistTabs` never enters the
  lifecycle/session queues, but complete tab snapshots are serialized on a
  dedicated persistence queue in reducer-dispatch order. An earlier failed
  snapshot reports its own failure without poisoning the queue, so a newer
  close/reorder snapshot can still become durable and an older concurrent
  write can never finish last and resurrect tabs.
- Backend stdout has separate ordered control and event lanes. Correlated RPC
  responses drain ahead of queued stream events (FIFO within each lane), while
  event/event order and the active OS write are never preempted. This prevents
  bulk tool/stream output from starving lifecycle and persistence RPCs. Session
  snapshot fitting occurs before enqueue and preserves the producer's existing
  event-before-ack enqueue order; the response-priority lane may still deliver
  the acknowledgement first, which the host already tolerates. `session.create`,
  `session.duplicate`, and `session.truncateAfter` correlated results contain
  only `{ ok, sessionPath }`. `session.opened` remains authoritative for the
  snapshot, while a successful create/duplicate acknowledgement may reconcile
  the pending path first when event publication is delayed or fails after
  runtime commit; the trailing event then hydrates metadata without repeating
  path replacement or queue drain. The durable create/duplicate commit occurs
  only after the coordinator has retained the process-local cold manager; it
  does not depend on execution-runtime bootstrap. If its full lossless transcript cannot fit
  after the mutation commits, the event is an explicit metadata-only
  `snapshotUnavailable` snapshot (and the host surfaces its notice) rather than
  converting the successful mutation into a failed RPC.
- `session.list`, `session.open`, `session.preload`, transcript paging, durable detail retrieval, cold forget, configured `models.list`, `session.create`, `session.duplicate`, and idle cold `session.truncateAfter` are runtime-free coordinator operations. One generation-scoped `ColdSessionStore` opens/revalidates durable files through `SessionManager`; it never creates `AgentSessionServices`, subscribes to SDK events, or reports busy work. Create/duplicate/truncate retain their exact process-local manager and creation reason transactionally until worker readiness, and publish `runtimeReady:false` with the existing selection/operation fields and acknowledgement shape. Cold truncate preserves the exact target exclusion plus durable model/thinking restoration and emits a post-commit `session.opened`; isolated hot truncate synchronously marks the route transitioning before awaiting interrupt, so same-target retries join while every other concurrent command receives `SESSION_TRANSITION_IN_PROGRESS` and cannot reach the old worker. It then quiesces and confirms the old worker/lease release, performs the coordinator cold rewrite, and publishes a fresh worker's runtime-ready snapshot before acknowledging; pre-retirement failure restores the verified old route, while post-retirement promotion failure remains retryable cold. Cold read/write publication rechecks coordinator generation, path ownership, and durable fingerprint at the final event/write boundary, so stale cold `busy:false` pages, lists, opened snapshots, and obsolete details cannot escape after mutation or promotion. Hot payloads carry `runtimeReady:true`. The configured cold model catalog is provisional: it describes `models.json`, not credential-filtered runtime availability.
- The hot-transition fence excludes two non-conflicting actions: `session.viewed` remains an immediate runtime-free metadata update, and `message.interrupt` may cancel work waiting to enter a transition before targeting only the resulting current owner (or succeeding as an idle no-op). A compound `message.edit` installs its transition synchronously, validates the selected entry against the current authoritative branch, quiesces and retires the old owner, records commit at the atomic rename, promotes a fresh owner, and sends the replacement before releasing the transition. A local JSON-RPC timeout or cancellation is never commit evidence. The host retains the stable operation and optimistic replacement, reconciles through `operation.status`, and restores the old tail/editor only when the coordinator reports `committed:false`.
- Concurrent first execution mutations for the same cold session share one in-flight promotion. Promotion reserves without irreversibly consuming the retained manager/reason, creates exactly one worker runtime/subscription, and commits the grant only after bounded runtime-ready `session.opened` publication; failed startup returns to retryable cold ownership. SDK replacement atomically rekeys coordinator roots, supervisor/client lease identity, and host tab selection using `replacesSessionPath`; after commit the worker must send the exact authorization nonce back through correlated `ownership.consume`/`ownership.consumed` frames. The coordinator accepts that owner/path/revision/nonce exactly once before the SDK may activate or write the destination, and runtime readiness is rejected until consumption. A lost acknowledgement fails the worker closed. The committed source returns cold independently while stale writes remain lease-rejected. Browse publication rechecks the owner and may not publish a cold `busy:false` snapshot after promotion starts.
- Provider network admission and circuits are coordinator-authoritative and correlated per fetch attempt. Capacity is enforced independently per configured provider across all workers and updates in place. Bounded response/failure observations feed one global provider circuit; after reset exactly one half-open probe owns admission until it settles. Cancellation is not a failure. A worker races queued admission against the fetch `AbortSignal`; cancellation sends `provider.cancel`, removes only that queued request or releases its just-granted lease exactly once, and settles the original acquire as cancellation. A completed interrupt cannot later receive or use a stale grant, an active response-body lease is retained until body settlement or confirmed worker process-tree death, and an isolated worker never installs independent admission/circuit capacity.
- Cold browse refreshes predecessor identity on every actual selection transition (including revisiting an already browsed cold path); same-path reselection leaves the prior real predecessor intact. Host-local snapshot-known selection uses `session.viewed` rather than duplicating `session.open`; the request is written immediately after the synchronous local state change, so a following execution request observes it in JSONL order. Its explicit host-observed predecessor remains correct even while an older cold open is still reading. Delayed promotion consumes that captured path and never identifies the currently viewed session as its own predecessor. Forget and backend-generation shutdown tombstone/fence both browse and promotion publication.
- Tool-call lifecycle is monotonic in `LivePipelineState`: late draft progress after `aborting`, late execution progress/start envelopes, and post-terminal updates cannot replace a durability-confirmed terminal or revive its tombstoned attempt. Projection represents each provisional draft as an ordered `ToolCall`-shaped row with `drafting`/`ready` status and phase, stable ID, and faithful raw argument text; incomplete JSON is never parsed into authoritative input. Stable parallel-group IDs, execution/sequence/phase commit metadata, and typed per-record bounded previews are carried by the canonical live record. The backend carries its canonical `previewBytes`, active-preview aggregate, and complete-checkpoint byte total on progress envelopes; the host stores per-execution and per-turn cached counts, validates arithmetic/bounds, and updates only the changed execution. Structural patches never stringify the reconstructed accumulated preview merely to enforce aggregate capacity. Checkpoint validation recomputes actual serialized bytes once because it is recovery-only, requires them not to exceed the backend's conservative total, and rebuilds trustworthy counters before queued envelope replay. Completed tool history may grow for the duration of a valid turn; safety is enforced by semantic payload compaction and total checkpoint bytes rather than an arbitrary completed-tool count. Supported semantic consumers skip legacy transcript `ToolCall`/terminal mutation while retaining analytics, file-change, and notice side effects. Raw/cyclic/BigInt SDK `onUpdate` values never cross into the host. Opaque transport-bound progress markers cannot replace an earlier
  renderable live result; cyclic/BigInt progress is converted to JSON-safe data
  while preserving subagent lifecycle details.
- Subagent progress is the exception to tail-only tool previews: while the complete parent recovery checkpoint remains below its 30 MiB allocation within the shared 32 MiB transport-record ceiling, the backend canonical state retains every child and the complete recursively renderable child transcript (reasoning, tool inputs/results, nested subagents, reply text, lifecycle, usage, and accounting metadata). Only the first progress record normally transports that complete snapshot; later records transport structural changes, including appended streamed text/reasoning and nested message/tool-result mutations. Raw cyclic, BigInt, non-finite, function, symbol, or throwing SDK values are converted to explicit JSON-safe representations before diffing. The parent-facing terminal details persist the same transcript without lossy result compaction. A completed nested tool result is serialized once in its authoritative `toolResult` message rather than duplicated on the matching assistant tool-call part; running inline progress remains until that durable result exists. Collapsed webview cards keep those bodies unmounted and expanded threads continue to render the host-assembled recursive transcript. Under blocked stdout, only contiguous same-tool v7 progress ranges may be composed into one equivalent patch; control/lifecycle records remain FIFO, terminal records remain durable and ordered, and no patch may skip an intervening lifecycle record. A durability-confirmed `tool.finished` side-effect event that still cannot fit its 30 MiB producer budget carries an explicit bounded `$toolResult`/`$toolInput` representation before it reaches the fatal JSONL writer. Crossing the hard transport ceiling is surfaced as an explicit protocol/transport failure; it must never be presented as a plausible complete snippet.
- A subagent child's `exitCode` owns its running/terminal lifecycle;
  `runningTools` is activity detail only. Every terminal path clears live tool
  and streaming flags. Parent interruption is retained as `stopReason: aborted`
  and renders as `Interrupted`, distinct from a failed child. A failed parallel
  tool does not relabel siblings whose own child results completed.
- A retry that exceeds the backend's existing delay-plus-grace watchdog is
  terminalized automatically: all exposed billable windows are aborted, SDK
  teardown gets a bounded five-second grace, and the backend emits an
  interrupted message plus `busy=false`. `RETRY_STUCK` is therefore a terminal
  recovery event, never a warning that leaves the session busy indefinitely.
- An assistant `message_end` error is only a candidate terminal until the
  following `agent_end` establishes `willRetry:false`. A retrying error cannot
  create a terminal tombstone for the still-running request; the live
  accumulator remains authoritative across attempts, and only the final failed
  attempt is committed as the durable error terminal.

## Deferred Trigger Delivery

- Timer and `session_finished` wakes use a durable per-trigger filesystem claim
  before dispatch. A real user prompt consumes `user_input` through that same
  claim and remains the only prompt; trigger consumption never adds a synthetic
  follow-up for `user_input`.
- Every new claim records the registry instance, owner PID, and claim time.
  Synthetic delivery fsyncs a `dispatch-started` boundary before entering the
  ordinary `Send` path; a `user_input` claim records that boundary immediately
  because its prompt was already dispatched.
- Registry startup/reload may release a claim only when the owner process is
  confirmed dead and no durable dispatch boundary exists. It replays the exact
  claim after confirming death, persists an idempotent claim for artifact-only
  crash windows, then makes the retryable release durable before the old
  artifact is removed, so two recovering hosts
  still race through the same atomic claim before any retry dispatch. A healthy
  owner, unknown/permission-denied liveness, PID reuse, a legacy owner without a
  PID, or any dispatch-started claim remains fail-closed.
- `ViewState.deferredTriggers` distinguishes safe dead-owner recovery from an
  acknowledgement-ambiguous claim. Safe recovery is retryable and an open
  watcher retries its timer/`session_finished` wake on the next event-loop turn;
  a closed watcher retains it until reopen. Ambiguous delivery blocks automatic
  retry and remains cancellable. Synthetic retries retain their message metadata
  and `user_input` continues to wait for one real prompt.

## Queued Follow-ups

- Sends accepted while a session is already running remain optimistic `queued` transcript messages until the backend reports delivery.
- While the current assistant turn is live, transcript projection places queued follow-ups after that turn, at the boundary where the backend will deliver them, rather than before the in-progress output.
- Delivery reconciliation is FIFO, matching the SDK's steering/follow-up queue order. Interrupt and queue-clear operations remove queued optimistic messages and their pending rollback snapshots.
- Queued follow-ups remain editable without interrupting or truncating the active turn. Because the SDK exposes only whole-queue clearing, an edit atomically replaces the ordered backend queue and preserves every message's local delivery correlation.
- Queue replacement compares the host's complete ordered local-id snapshot with the backend's authoritative undelivered correlation queue before clearing anything. If delivery already consumed an item, replacement fails without re-enqueueing an edited duplicate; the delivery event closes any stale editor and promotes the original row.
- Queued user rows do not own the current turn's pruning or activity state. Pending assistant/activity UI stays attached before the queued boundary until delivery.

## Reducer Purity

- The reducer is pure: `(State, Event) → { state, effects }`. No I/O, no `Date.now()`, no randomness.
- Side effects only happen inside the EffectRunner.
- An `EffectResult` handler in the reducer may return new effects, but those are queued asynchronously by the runner; the reducer never synchronously awaits another effect.

## Optimistic Reconciliation

- Optimistic mutations (send, edit) are tagged with a `corrId` that correlates the command, the pending state entry, and the eventual `EffectResult`.
- `state.pending.ops: Record<corrId, PendingOp>` tracks in-flight optimistic operations with rollback snapshots.
- On send RPC success: move the rollback snapshot from `pending.ops[corrId]` to `pending.promoted[corrId]` and mark the stable operation accepted; acceptance is not commit and does not terminalize the operation. Other mutation kinds retain their documented success promotion behavior.
- On definitive pre-commit RPC failure: revert via `state.pending.ops[corrId]` — remove the optimistic transcript entry by `localId`, restore `previousSummary`, and drop the entry. A local transport deadline is ambiguous and is not this failure path. Send rollback fires a `sendRejected` imperative for the bottom composer. Edit rollback instead restores the submitted inline-editor `{ messageId, text, inputs }` in host state and projects it back into the original transcript row; it must never repurpose `sendRejected`. For edit, only backend `committed:false` is rollback authority. Unknown or committed outcomes keep the optimistic replacement and never resurrect the removed tail.
- Backend events arriving before `SendRpcResult` are applied normally — the pending user message is already in the transcript, so assistant deltas append after it. A first `MessageStarted` / applied `turn.started` before the acknowledgement commits the oldest non-queued `pending.ops` owner for that session and clears its send timer; the later acknowledgement is a no-op. A correlated `MessageFinished` / `MessageAborted` that is the first observable terminal boundary settles the operation and timer the same way, without rolling back the persisted user message. Session mutation FIFO makes this early-boundary fallback unambiguous.

### Two failure windows for `send`

> `message.send` resolves as soon as the prompt is *queued* (before the pruning
> prepass). `state.pending.promoted` retains rollback ownership after acceptance,
> while `ArchState.operations[operationId]` remains non-terminal until correlated
> commit evidence. Local timer expiry now enters registry ambiguity and starts
> read-only reconciliation; it is not synthesized as `PreflightFailed`.
> The existing `sendRejected.inputs` payload
> and the webview composer-input restore (plus composer clear-at-send): the
> post-ack rollback restores host-side `pendingComposerInputsBySession`
> from `pending.promoted[corrId].inputs` AND carries `inputs` on the
> `sendRejected` imperative; the pre-ack `SendResult{ok:false}` path mirrors
> it (restores from `pending.ops[corrId].inputs`). When the rejected session is
> active, the webview stages the imperative's `inputs` as a transient override
> of `pendingComposerInputs` until the next snapshot confirms. A background
> rejection must not project those inputs into the active composer; its
> host-owned per-session inputs appear when that session becomes active. The
> subsection below describes the full state.

`message.send` will resolve as soon as the prompt is *queued* (before the pruning prepass), so an optimistic send will have two failure windows, not one:

1. **Pre-ack failure** — the `message.send` RPC receives a definitive rejection. Revert via `state.pending.ops[corrId]`, exactly as the legacy contract describes. `SendResult{ok:false}` is the trigger. A local `RequestTimeoutError` is not definitive rejection evidence because cancelling the host waiter does not cancel backend execution; the runner retains the pending operation and watchdog so the first semantic start/terminal boundary can settle it without restoring an already-sent draft.
2. **Post-ack, pre-commit failure** — the RPC succeeded but the prepass then fails. The trigger is a dedicated `PreflightFailed{corrId, sessionPath, requestId, error}` event, **not** a reused `SendResult{ok:false}` (the RPC genuinely succeeded; the prepass is a distinct phase). On `SendResult{ok:true}` the rollback snapshot is **not** deleted — it moves from `state.pending.ops[corrId]` to `state.pending.promoted[corrId]`, which retains the snapshot and composer-input restore payload until the turn commits.

**Commit point:** a promoted send commits at the **first streaming event** (`MessageStarted`/first `Delta`) for its `requestId`. At that point `pending.promoted[corrId]` is dropped and a later prepass/turn failure becomes an in-turn error (surfaced by the error mapper), never a rollback. This bounds the rollback window so a flaky prepass cannot yank a turn the user has already watched start streaming.

A post-ack, pre-commit `PreflightFailed` must: remove the optimistic transcript entry by `pending.promoted[corrId].localId`, restore `pending.promoted[corrId].previousSummary`, restore `pendingComposerInputsBySession[sessionPath]` from `pending.promoted[corrId].inputs`, clear `pending.requestIdToLocalId[requestId]`, fire a `sendRejected` imperative (carrying `inputs`), and surface a plain-language error.

**Timer ownership:** a send has phase-scoped timers, never racing. `RequestTracker` bounds how long the host waits for the queue-time RPC acknowledgement; timeout marks the stable operation ambiguous, retains optimistic ownership, and starts read-only status reconciliation. One send-timer bounds acknowledgement/prepass/model-start observation. `preflight-succeeded` replaces its prepass budget with a model-start budget. On expiry, a registry-backed send again becomes ambiguous and reconciles; timer expiry alone never emits rollback-owning `PreflightFailed`. The timer clears at the first correlated commit boundary. Edit and interrupt acknowledgement deadlines use the same registry-backed ambiguity/status path; edit status carries the destructive commit bit and interrupt status carries full-barrier settlement. Definitive pre-commit rejection and confirmed generation death own send rollback, while edit rollback additionally requires `committed:false`. Immutable operation terminals prevent late contradictory observations from producing a second outcome. Independently, the backend forwards persisted pruning-result metadata at the first lifecycle boundary that observes it with duplicate suppression.

## Webview-Local State

The webview must not hold logic state in local `useState`/`useReducer`. Only the following ephemeral UI concerns are allowed as webview-local state:

- **contextMenu** — position and type of the currently open context menu (dismissed on click-outside/Escape)
- **peek / hover overlay** — transient overlay visibility for the changed-files rail (and analogous hover-peek surfaces), dismissed on mouse-leave / tap-outside / Escape. It is an overlay, not a layout push — it reserves no horizontal space; only an explicit pin (`ViewState.fileChangesExpanded`) durably reserves space. The moral equivalent of `contextMenu`.
- **scrollPosition / autoScroll** — viewport scroll tracking
- **input focus / caret position** — DOM focus state
- **drag state** — transient tab drag-and-drop position
- **animation / transition state** — CSS transition tracking
- **protocol-sync bookkeeping** — `lastRevisionRef`, `awaitingSnapshotRef`, `hostInstanceIdRef`, the terminal protocol-compatibility latch, mounted-inline-prompt request counts (DOM-presence only; host pending requests remain authoritative), pending-draft-restore tracking (keyed by session; it survives same-host tab switches and is cleared on host replacement), pending-composer-inputs-restore tracking (Brief C: for the active session only, a transient render override of `pendingComposerInputs` staged between a `sendRejected` imperative and the next confirming snapshot — the analog of draft-restore), in-flight `corrId` set for UI gating, and the bounded ephemeral cache of explicitly fetched lazy details (durable/live source remains authoritative; cache loss triggers re-fetch)
- **derived UI telemetry** — FPS counters, render-timing buffers. Token-rate measurement is not webview-local: it runs host-side in `TokenRateService`, which ticks every running session — including ones that are not the active/selected tab — using the transcripts the host already holds, and posts the per-session states as `ViewState.tokenRateBySession`. Session working time is likewise host-owned: `ViewState.workingTimeBySession` carries settled agent-busy wall time, measured preflight model time that occurs before the backend busy boundary, the current interval's host timestamp, and optional run-telemetry attribution for generation, non-overlapping tool execution, retry waits, timed auxiliary model calls, per-tool cumulative call time, and cumulative subagent time. While tools execute, the host also carries the current non-overlapping tool-interval boundary and active call starts so MCP, subagent, and ordinary tool time remains attributable before terminal telemetry arrives. The webview may tick those active durations locally and derive the unattributed remainder for display, but it never creates timing boundaries or accumulates authoritative time. Per-tool call totals may overlap under parallel execution and therefore remain detail beneath the non-overlapping tool wall-time category. Subagent time is an intentionally additive agent-seconds detail outside the wall-time bar: every terminal attempt and its reported retry backoff contributes independently, including attempts that ran in parallel or nested inside another subagent, so it may overlap both the parent session and other subagent time.
- **per-keystroke draft buffer** inside an active input (the committed draft on blur/send/tab-switch is host state; the live keystroke buffer is not). An actively edited transcript row is pinned in the virtualizer and in the host's loaded transcript window: new paging is deferred, incoming page/tail replacements that omit the row are held until Cancel (or discarded when Save establishes newer authority), and window-budget culling retains it. Scrolling, streaming snapshots, and metadata refreshes therefore cannot unmount that local buffer; after submitted-edit rollback, the host projects the submitted text and attachments into a newly reopened inline editor.
- **optimistic user message overlay** — pending user messages shown instantly before the host confirms them. The webview generates a `localId`, sends it with the `send` protocol message, and displays the message in the transcript immediately. When the host state arrives containing a message with that `localId`, the optimistic overlay entry is reconciled away. On `sendRejected`, the overlay entry is removed and the draft is restored.
- **pinned-group dropdown open state** — which pinned-group chip (if any) has its member dropdown open (`openGroupPath`, keyed by a member path). Transient local UI only: it stays open across member selection and active-session change, re-associates with the surviving group when its former first member is dragged out, and closes on outside pointerdown / Escape / host replacement (a group dissolving below 2 or merging away with no surviving ≥2 group closes it).

All other state (editing, draft content, session selection, model settings, prefs) lives in the host store and reaches the webview via ViewState snapshots.

- Subagent nesting controls are host-owned preferences. In particular,
  `subagentBucketCanSpawn` is a complete `{ small, medium, frontier }` boolean
  map that defaults missing or malformed tiers to `true`, is mirrored to every
  worker through `runtimePrefs.set`, and applies to the caller's effective
  subagent bucket. Active-parent fallback children inherit a subagent parent's
  bucket; root chats and their unclassified fallback children remain unrestricted.

## MCP Server State

- `ViewState.mcpServers` (host-owned `ArchState.settings.mcpServers`) is the
  effective MCP server list with merged `disabled` state, fetched from the
  backend (`mcp.list`, which reads the adapter's config files). The webview
  is passive: it renders the snapshot and requests refreshes via
  `mcpListRequested` (sent when an MCP surface opens). Global discovery runs
  independently of session worker recycling, so opening an MCP surface can
  render server rows without waiting for a prior session-scoped toggle to
  retire its worker.
- `ViewState.mcpServersStatus` (`'loading' | 'error' | 'ok'`, optional for
  legacy hosts — treat as `'ok'`) is the discovery state of that list:
  `'loading'` while a fetch is in flight (or before the first fetch),
  `'error'` after a failed fetch/toggle (the cached rows stay visible and a
  Refresh action is offered), `'ok'` after a successful global fetch. A later
  session-hydration success does not mask a failed global fetch. The webview
  must not render `No MCP servers configured` while the list is merely
  unknown/loading/failed.
- `ViewState.mcpPendingApply` is true after a per-server toggle wrote a
  `.pi/mcp.json` `disabled` override that the adapter has not re-read yet
  (applies on the next session reload / backend restart). It is set only by
  the `McpServersUpdated` response event when a toggle actually changed the
  override; a plain `mcp.list` read (or a no-op toggle) does not reload the
  adapter, so the flag is preserved across refreshes and cleared when the
  backend restarts (`BackendReadyChanged` ready).
- Toggling (`mcpSetServerEnabled`) marks discovery as loading but never
  changes the cached server list or disabled state optimistically; the backend
  response (`McpServersUpdated`) is the single authority. A failed
  fetch/toggle keeps the cached list and flag and sets `mcpServersStatus` to
  `'error'`.

### Session-scoped MCP server toggles

The toolbar MCP dropdown is session-scoped; Settings → MCP stays the global
surface. The two scopes never share a write path:

- `ViewState.mcpSessionServers` (host-owned
  `ArchState.settings.mcpSessionOverridesBySession` merged into the global
  list by the projection) is the active session's effective server list:
  globally/project-disabled servers stay disabled, and a session override can
  hide an otherwise-enabled server. The session map is a plain
  `Record<sessionPath, Record<serverName, boolean>>` host field; it is
  rehydrated from the artifact after host restart, and the backend artifact is
  removed when the session is forgotten. A menu refresh publishes the global
  list first, then queues persisted-session hydration after already-pending
  writes on that session's FIFO; later toggles stay ordered behind that read
  and remain authoritative when their writes settle.
- Toggling (`mcpSetServerEnabledForSession`, addressed to the toggled
  session) optimistically seeds the session map, then emits an
  `McpSetSessionServerRpc` effect carrying the FULL desired override set plus
  `recycle: !running` (the backend may only retire an idle session's worker).
  The backend response `McpSessionServersUpdated` replaces the session map
  authoritatively and sets per-session pending state.
- `ViewState.mcpSessionPendingApply` is true when the toggle's worker recycle
  was refused (session busy, cold, or transitioned away) or the backend write
  failed — the override applies at the next session reload / idle recycle.
  The host retries once per idle transition (`BusyChanged` running=false);
  the hint clears on a successful recycle (`recycled: true`) and on backend
  restart.
- Per-session toggle writes never touch `.pi/mcp.json` (global scope). The
  backend translates the override set into a session-scoped config artifact
  (`<sessionPath>.mcp-overrides.json`), passed to that session's worker as
  `--mcp-config` so the adapter substitutes only its highest-precedence
  discovery layer for that session. The artifact carries flags (and a copy of
  the Pi agent-dir layer it replaces) — never server credentials.

## Multi-Renderer Ownership

The host may serve the same UI to several renderer surfaces: the VS Code sidebar and, later, loopback-served browsers. The sidebar and browser are **passive renderers of one shared host state** — there is no second state authority and no collaborative-editing model.

- **Shared host identity vs per-renderer delivery identity.** `hostInstanceId` is the shared extension-host incarnation. Each renderer additionally owns a host-assigned `rendererId` and a `rendererGeneration` (reload/reconnect fence). Envelope `revision`s are scoped per renderer; evidence from renderer A can never settle renderer B even when their numeric revisions match. Inbound evidence is routed by the transport registration first, then checked against that renderer's accepted ledger.
- **One shared projection, per-renderer envelopes.** One logical render produces one projected/JSON-safe `ViewState` body shared by all renderer sessions; each session assembles its own bounded envelope carrying its own `rendererId`, `rendererGeneration`, and `revision`. VS Code receives an object envelope through structured clone; browser transports receive JSON envelopes.
- **Independent delivery state.** Each renderer owns its own `StateDeliveryController`, readiness probe, commit watchdog, pending imperatives, and visibility belief. A blocked, hidden, disconnected, or broken renderer never delays another renderer's delivery, reducer/effect dispatch, backend RPC, or agent execution. Blocked snapshots are dropped/coalesced (latest-wins), never queued as a backlog.
- **Shared host logic state.** `activeSessionPath`, tabs, settings, editing, `pendingComposerInputs`, notices, and extension-UI ownership remain host-owned `ArchState`. A host-state change caused by any renderer is projected to all renderers. Selecting a session in either surface selects it in both.
- **Renderer-local state.** Scroll, focus, caret, hover, open menus, and the other § Webview-Local State allowlisted concerns remain independent per surface.
- **Targeted imperatives.** `sendRejected` draft/optimistic-overlay restoration, lazy-detail responses, Phase 5 detail streams, and `rendererNotice` feedback route to the initiating renderer only. All renderer hubs share one `hostInstanceId`; detail owners are released before their renderer generation is invalidated by reload/disconnect. Global notices and authoritative state remain snapshot-driven.
- **Browser command acknowledgement.** Every schema-valid browser application command that reaches routing has exactly one host decision and one host-side `commandAck` emission (`accepted` or `rejected`); the client observes `accepted`/`rejected` when delivered or `unknown` when a close loses the ack. Reconnect never replays accepted/unknown commands; the bounded host command-decision ledger answers read-only `commandStatusRequest`s and never executes commands as part of reconciliation.
- **Browser ingress is fail-closed.** Browser messages are validated by the exact bounded `validateBrowserToHostMessage` schema before `MessageRouter`: unknown fields rejected, wrong types rejected, bounded strings/arrays/depth, base64 only in the allowlisted `imageBlob`/`ComposerInputDraft` image fields, decoded images ≤ 10 MiB each and ≤ 20 MiB aggregate, full frames ≤ 32 MiB, and closed `extensionUiResponse` payloads. The first legal client frame is a `ready` carrying the renderer's compiled build id; lifecycle traffic cannot clear the handshake deadline. The browser likewise accepts only one complete, protocol-compatible `rendererHello` before any state or imperative. Build skew is accepted; malformed greetings, protocol skew, asset skew, repeated schema violations, or handshake-order violations close and latch the socket without a stale reconnect loop.
- **Completion attention is host-owned and arbitrated** among visible eligible renderers (latest focus epoch, then latest visible browser, then the visible sidebar); all-hidden yields zero renderer sound/UI recipients. VS Code window focus state is not consulted.

## Pinned-Tab Groups

- Pinned-tab group **membership and strip order are host-owned and persistent**: `pinnedTabPaths` (flat order) and `pinnedTabGroups` (the partition) live in the host store and are persisted via `PersistTabs`. A group is unnamed and identified by any member path; its members appear contiguously in `pinnedTabPaths` in group order, and groups with fewer than 2 members are dissolved. The webview derives the renderable pinned items (standalone chips + group chips) from these two host-owned fields and never mutates them locally.
- The open **dropdown is the only allowlisted local transient** for groups (see Webview-Local State): it is keyed by a member path, remains open across member selection and active-session change, re-associates with the surviving group when its former first member is dragged out, and closes on outside pointerdown / Escape / host replacement (dissolution/merge with no surviving ≥2 group).

## Extension UI Requests

- Every pending interactive extension-UI request for the active session has an
  actionable surface. A tool/subagent-owned request renders inline when its
  exact prompt is mounted; otherwise a fixed fallback appears above the
  composer. Inline ownership alone is insufficient because the card can be
  collapsed, virtualized, delayed, or stale while the tab already signals that
  the session is waiting for input.
- Requests without an inline owner retain priority when several requests are
  pending; if all requests are inline-owned, the fixed fallback uses the oldest
  request whose exact inline prompt is not mounted. One visible sibling must
  not hide another collapsed/virtualized question.

## Notice Surfacing

- The host owns a single notice record in `settings`: `notice` (short, user-facing summary, `string | null`), `noticeKind` (Brief H failure category for recovery buttons, `NoticeKind | null`), `noticeRaw` (the full host-side backend error string, `string | null`), and `noticeSessionPath` (the owning chat, or `null` for application-wide notices). A session-owned notice is projected only while its owner is active; this prevents a background failure's Retry action from operating on another chat's composer.
- Neither the short `notice` summary nor renderer-projected `noticeRaw` contains internal `req-NN` correlation ids (Brief H criterion 1). The raw request identity remains in the host log; projection strips it and redacts credentials before the webview boundary, so "show raw" remains useful without exposing internal transport bookkeeping or secrets.
- Invariant: `noticeRaw` is non-null only when `notice` is an error notice (set at the send/edit/prepass error sites, `handleError`, and `revertSetModel`). Plain `NoticeShown` notices (info/warnings, including `notice: null` clears) always set `noticeRaw = null` so a stale "show raw" can't outlive its notice.
- `dismissNotice` clears all four together. A non-error `NoticeShown` clears `noticeKind`, `noticeRaw`, and `noticeSessionPath` together (a plain info banner carries no recovery actions and no raw detail).
- A correlated RPC failure is surfaced through its owning result path (one rollback/notice) and recorded once by the backend-client response observer. The backend does not emit a second generic public error for that same request. Later asynchronous `operational-error` events carry their own incident identity; the host uses one backend-generation-scoped identity registry across both channels so a legacy same-request echo cannot duplicate analytics or notice.
- Backend `operational-error` events retain their stable code, request correlation, and optional root-cause `detail` in `noticeRaw`; only the plain-language `message` becomes the short notice. Provider HTTP/transport observations below the SDK are correlated to the active session and surfaced immediately with provider, HTTP status/classification, and retry/reset time. Quota exhaustion is distinct from a transient 429 and has a bounded settlement watchdog; it cannot remain an invisible SDK backoff. Provider semantic-inactivity timeouts include provider/model, the elapsed inactivity threshold, what semantic signals were absent, and the last SDK provider/retry error when one was observed. If no provider error event preceded the silence, the detail says so rather than inventing a cause.
- The projection surfaces all three as `ViewState.notice`, `ViewState.noticeKind`, and credential-redacted `ViewState.noticeRaw`. The webview's `NoticeBanner` renders the short summary, recovery action buttons (from `kind`), and — when `noticeRaw` differs from `notice` — a "More" toggle that reveals the sanitized diagnostic in a scrollable monospaced block.
